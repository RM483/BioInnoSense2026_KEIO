## 1. プロジェクト概要

**HydroPaw** = 犬の呼気に含まれる水素(H2)ガスを測定し、腸内環境の状態を毎日そっと見守るデバイス＋アプリ。

犬の腸内細菌が食物繊維を発酵させると水素が発生し、血流に乗って肺から呼気として排出される。人間の医療では「呼気水素試験」として乳糖不耐症・小腸内細菌増殖症(SIBO)の診断に使われている確立した手法で、これを犬向けに、病院ではなく家庭で毎日測れるようにするのが本プロジェクト。

プロダクトとしての方針は「**数値ではなく意味を見せる**」。飼い主に「今日は12.3ppm」と言っても判断できないので、アプリは「安定」「やや高め」といった状態語と、普段との比較（トレンド）で伝える。数値は詳細画面にだけ置く。

## 2. システム全体像

センサからアプリまで、データは次の順に流れる。

```
[水素センサ] → [マイコン] → [BLE無線] → [アプリ(Web/スマホ)] → [画面表示]
```

そして重要な点として、**センサ＋マイコンの組み合わせが2系統ある**。どちらもアプリからは同じように見えるように作ってある（後述のHPPプロトコルが共通のため）。

| | 系統A（本命） | 系統B（別案・予備） |
|---|---|---|
| センサ | DGS2 970-Series（電気化学式） | FIS SB-19-00（半導体式) |
| マイコン | STM32L452（Leafonyボード） | Arduino Uno R4 WiFi |
| センサ接続 | UART（デジタル・CSV文字列） | アナログ電圧 → ADC |
| BLE | AC02リーフ（BGAPI経由） | R4内蔵BLE（ArduinoBLE） |
| BLE広告名 | `Leaf_A_#...` | `Fuwan-R4` |
| 消費電力 | 小（電池運用も可） | ヒータ120mW常時（USB給電必須） |
| 定量性 | ppm絶対値に近い | 相対指標（較正で改善） |
| ソースの場所 | `firmware/` | `arduino_fis/` |

**なぜ2系統あるのか**: 系統Aが本命だが、電気化学センサは入手性・個体差・寿命の懸念があるため、中間発表の読み出し回路スライドで示した半導体式構成も並行して実装した。比較データが取れれば研究としての厚みも出る。

## 4. データの流れ（詳細）

### 4.1 系統A（STM32 + DGS2）

1. **センサ**: DGS2は1秒ごとにUART(9600bps)でCSV文字列を送ってくる。
   ```
   091323010122, 7410, 3093, 5259, 32373, 29012, 30722
   └シリアル番号  └H2   └温度  └湿度   └以下ADC生値
                  (ppb) (℃×100)(%×100)
   ```
2. **STM32**: 受信バイトをリングバッファに貯め、改行で1行にまとめ、CSVを解析して数値化する。
3. **呼気解析(BAP)**: 静かな状態のベースラインを学習 → 立ち上がり検出 → ピーク・面積・立ち上がり時間などを算出 → 品質スコアを付ける。
4. **BLE送信**: HPPというフレーム形式に詰めて、AC02リーフ経由でスマホ/PCへ送る。ライブ値は`EVT_DATA`、測定結果は`EVT_RESULT`。
5. **アプリ**: 受信して、ppb→ppm変換と「意味」への翻訳をして表示する。

### 4.2 HPPプロトコル（両系統共通）

`[SOF][長さ][種別][連番][ペイロード][CRC16]` の単純なバイナリフレーム。重要なイベントは受信確認(ACK)と自動再送(ARQ)付きで、BLEが一瞬切れても測定結果が失われない設計。**このプロトコルが共通なので、アプリは系統A/Bのどちらにも繋がる**（接続先のUUIDを切り替えるだけ）。

### 4.3 デバッグ用シリアルログ

STM32はUSART2（AZ01 USBリーフ経由）に人間可読のログを吐いている。BLEとは独立した「覗き窓」で、繋がなくても製品としては動く。Macでの見方:

```
( stty 115200; cat ) < /dev/cu.usbserial-AH07FW3T
```

出力例:
```
HydroPaw FW v1.0 boot
reset cause: PIN
optbytes: IWDG FROZEN in stop
BLE boot/disc -> advertise
DGS2 rx cols=7 parse=OK [091323010122, 7410, 3093, ...]
state 1 -> 2
sensor init OK sn=091323010122
BLE connected handle=1
BLE tx type=81 seq=1 len=13
```

## 5. いま機材に書き込まれているもの（2026-07-28時点）

### 5.1 STM32（系統A）

`firmware/` の最新をビルドしたもの。2026-07-27〜28に以下の変更を入れて書き込み済み:

| 変更 | 内容 | 理由 |
|---|---|---|
| SN検証の緩和 | シリアル番号が化けていても測定行を受理（非英数字は`?`に置換） | EEPROMが壊れた個体が実在したため。この個体でも測定値は正常だった |
| 生CSVのログ出力 | `DGS2 rx ... [生の行]` を出す | パース失敗時の原因切り分け用 |
| USB常時給電プロファイル | 自動スリープ・無通信自動停止・測定30分上限を**全て無効化** | 現行ハードはスリープするとBLEから起こせない。USB給電前提の運用にしたため |
| EEPROMダンプ要求 | 起動時に`e`コマンドを送りセンサの素性をログ出力 | ガス種・感度・工場較正値を確認するため（**未書き込み。次回ビルド時に反映**） |

**設定を戻したい場合**: すべて `firmware/Core/Inc/app_config.h` の定数1行で切り替わる。電池運用に戻すなら `CFG_IDLE_TO_SLEEP_MS` などを`0`から元の値（10000/60000/60000）に戻す。

### 5.2 Arduino R4（系統B）

`arduino_fis/` を書き込み済み。**注意: `config.h` の `FIS_SIM_SENSOR` が `1`（SIMモード）のままなら、実センサではなく合成データが流れる。** 実センサで測るときは `0` にして再書き込みすること。

### 5.3 アプリ（Webapp）

- 既定で**実機モード(BLE)**。`npm run dev` だけで実機に繋がる（以前は環境変数指定が必要で事故のもとだった）
- 接続先UUIDは**系統A（Leaf_A）用**に設定されている。系統Bを使うときは `webapp/src/providers/BleProvider.ts` の定数を`Fuwan`/`6e400001-...`に差し替える
- 設定画面に「ゼロ校正」ボタンあり（BLE接続時のみ表示）
- 測定中は20秒ごとに接続維持信号を送る

## 6. 動かし方

### 6.1 STM32のビルドと書き込み

1. **STM32CubeIDE**を開く（未インストールならST公式サイトから）
2. `File → Import → General → Existing Projects into Workspace` で `firmware/` を選択
3. プロジェクト右クリック → **Build Project**
   - 「Build Failed. 4 errors」と出るが、`_close/_read/_write is not implemented`の**誤検知**。`Finished building target: HydroPaw.elf` が出ていれば成功
4. 基板のスイッチを**PGM側**に切替 → **RST**ボタン
5. **STM32CubeProgrammer**を起動 → 左上でUART選択 → ポート`usbserial-...` → **Connect**
6. `Erasing & Programming` タブ → `firmware/Debug/HydroPaw.elf` を選択 → **Start Programming**
7. 完了したら**切断** → スイッチを**Run側** → **RST**

### 6.2 Arduino R4のビルドと書き込み

1. Arduino IDEで「ボードマネージャ → Arduino UNO R4 Boards」を導入
2. 「ライブラリマネージャ → ArduinoBLE」を導入
3. `arduino_fis/arduino_fis.ino` を開く（同フォルダの`.h/.cpp`も自動でコンパイルされる）
4. ボード=Arduino UNO R4 WiFi、ポート選択 → 書き込み
5. シリアルモニタ115200で `Fuwan-R4 (FIS SB-19) boot / advertising` を確認

### 6.3 Webアプリ（Mac）

```
cd webapp
npm install          # 初回のみ
npm run dev
```
Chromeで `http://localhost:5173` を開く。

### 6.4 Webアプリ（Windows）

必要なもの: Node.js LTS（https://nodejs.org）、Git、Chrome、Bluetooth内蔵PC

```
git clone https://github.com/RM483/BioInnoSense2026_KEIO.git
cd BioInnoSense2026_KEIO/webapp
npm install
npm run dev
```
Chromeで `http://localhost:5173` を開く。

**注意**: Web BluetoothはHTTPSまたはlocalhostでしか動かない。他のPCから`http://192.168.x.x:5173`で開くとBLEが使えないので、各PCでdevサーバーを立てるか、Firebase Hostingにデプロイして`https://`のURLで配る。**iPhoneのブラウザはWeb Bluetooth非対応**なので、iOSで実機接続したい場合はFlutterアプリのビルドが必要（Xcode要）。

### 6.5 測定の手順

1. デバイスにUSB給電（電源を入れる）
2. アプリを開く → 設定タブ →「接続する」→ デバイス選択（`Leaf_A_#...`）
3. ホームで犬を登録（初回のみ）
4. 「◯◯の測定をはじめる」→ ライブ値とグラフが流れる
5. 「終了する」で測定終了、結果が履歴に保存される

## 7. センサの扱い方（重要）

電気化学式センサは**通電してから安定するまで時間がかかる**。ここを知らないと「値がおかしい」と誤解する。

| 状況 | 必要な予熱時間 |
|---|---|
| 初回／数週間保管後 | **48時間**の連続通電（データシート推奨） |
| 一晩〜数日オフ | 数時間 |
| 数分〜1時間オフ（移動など） | 10〜30分 |

**実測した挙動（2026-07-27〜28）**: 新品センサを通電したところ、247ppm → 34 → 15 → 7 → 5.6 → 3.8 → 3.4ppm と12時間以上かけて単調に減少し、その後ほぼ横ばいになった。清浄大気の真値は約0.5ppmなので、残った3.4ppmが**ずれたゼロ点**。

**ゼロ校正の手順**
1. 値が下げ止まるまで待つ（数時間変化しなければOK）
2. 測定を**終了**する（測定中は校正コマンドが拒否される）
3. きれいな空気の場所で、設定タブ →「ゼロ校正」→ 実行
4. 再度測定して0付近になっていれば成功

**運用の推奨**: 常時USB給電しっぱなし。移動時はモバイルバッテリーで給電したまま運ぶと再安定待ちがゼロ。発表なら2日前に通電開始、前日にゼロ校正。

## 8. 現在わかっている問題・調査中の件

### 8.1 【最重要・未解決】標準ガスに反応しない

**症状**: 研究室で1000ppmのH2を暴露 → 7.6ppmまでしか上がらない。空気で50ppmに希釈しても**まったく変化しない**。一方で、**息を吹きかけると反応する**。

**確認済み**: ソフトウェア側は無罪。センサのCSV生値をそのまま表示しているだけで、加工は一切していない（シリアルログの生値とアプリ表示が一致することで確認可能）。

**残っている仮説**
1. **センサのガス種が違う** — DGS2 970シリーズはCO/O3/NO2/H2S/H2など同型番でガス種違いがある。H2用でなければ当然反応しない。→ **EEPROMダンプ(`e`コマンド)で確定できる。FWに実装済み・未書き込み**
2. **吸気口が塞がっている** — 出荷時の保護シールが残っている個体がある。目視確認すること
3. **「呼気への反応」が湿度アーティファクト** — 湿度・温度の急変への交差応答を水素応答と誤認している可能性。→ **お湯の湯気（H2ゼロの湿った空気）を当てて同じように反応したら、この線が濃厚**
4. **ガスがセンサ面に到達していない** — 配管の当て方・流量・暴露時間。呼気は「至近距離で強く吹き付け」なので条件が全く違う

**次にやるべき切り分け（この順で）**
1. 湯気テスト（2分、FW変更不要）
2. センサ吸気口の目視確認
3. EEPROMダンプ用FWをビルド＆書き込み → ログを確認

**注意**: 電気化学センサは酸素がないと反応しない（作用極でH2酸化、対極でO2還元という電池反応のため）。純水素を当てると濃度最大でも無反応になるのは正常。標準ガスは必ず**空気ベース**を使うこと。

### 8.2 測定レンジ

DGS2 H2の測定レンジは**0〜100ppm**（絶対最大120ppm）。1000ppmはレンジ外なので較正データに使えないうえ、過大暴露は電極の分極を招き、その後しばらく読み値がずれる。**較正は1 / 10 / 50 / 100ppm** の系列で行うこと。

### 8.3 シリアル番号が化ける個体

最初に使った個体は、SNフィールドが制御文字混じりの化けた値になっていた（測定値そのものは正常）。FW側で受理するよう対策済み。予備個体では正常な12桁が読めたため、個体のEEPROM不良と判断。

### 8.4 STOP2から復帰できない設計課題

現行ハードは低消費電力モード(STOP2)に入るとBLE(UART4)からは復帰できない（Wake源がUSART2のみ）。そのためUSB給電前提の設定（自動スリープ無効）にしてある。電池運用を目指すなら、UART4のStopモードWake対応が先に必要。

### 8.5 しきい値がすべて仮値

「安定/やや高め」の判定境界（10/20ppm）、呼気検出のしきい値などは**すべてPROVISIONAL（実犬較正前の仮値）**。発表で聞かれたら「較正実験で確定予定の暫定値」と正直に答えるのが正しい。

## 10. トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| `sensor init FAILED (no response)` | センサからデータが来ていない。①配線（DGS2のTXD→D9, RXD→D8のクロス接続）②GND共通 ③USB抜き差しで電源入れ直し |
| `DGS2 rx cols=7 parse=FAIL` | データは来ているがCSVの中身が想定外。ログの`[...]`部分に生の行が出るのでそれを見る |
| デバイスがBLE一覧に出ない | 本体RSTを押してから60秒以内に接続操作。MacのBluetooth ON確認 |
| アプリが「デモ (実機なし)」表示 | 古いバージョン。`git pull`して`npm run dev`し直す（現在は既定が実機モード） |
| シリアルモニタが文字化け | ボーレート違い。`( stty 115200; cat ) < /dev/cu.usbserial-...` の形で開く |
| `screen`で`Resource busy` | CubeProgrammerがポートを掴んでいる。切断するかアプリごと終了。`lsof /dev/cu.usbserial-...`で犯人を特定できる |
| ビルドで「4 errors」 | `_close/_read/_write`絡みなら誤検知。`.elf`が生成されていれば成功 |
| 値が異常に高い（数十〜数百ppm） | 通電直後のドリフト。7章参照。時間で下がる |
| 測定が勝手に止まる | 古いFW。現在は自動停止を無効化済み。書き込み直す |

## 11. 用語集

| 用語 | 意味 |
|---|---|
| **DGS2** | SPEC Sensors社の電気化学式ガスセンサモジュール。UARTでCSVを吐く |
| **FIS SB-19** | FIS社の半導体式(SnO2)水素センサ。抵抗値が濃度で変わる |
| **Leafony** | 小型の積層式IoTボードシリーズ。STM32リーフ(AP03)、BLEリーフ(AC02)、USBリーフ(AZ01)などを重ねて使う |
| **AC02 / AZ01 / AP03** | 順にBLEリーフ / USBシリアルリーフ / STM32マイコンリーフ |
| **HPP** | HydroPaw Protocol。自作のBLEフレーム形式（CRC16・ACK/再送付き） |
| **BAP** | Breath Analysis Pipeline。呼気波形から特徴量と品質スコアを出す解析処理 |
| **BGAPI** | Silicon Labs製BLEモジュール(AC02)を制御するバイナリコマンド体系 |
| **ppb / ppm** | 濃度単位。1ppm = 1000ppb。FW内部はppb、アプリ表示はppm |
| **ratiometric** | 電源電圧の変動をキャンセルする測定方式（比率で見る） |
| **ゼロ校正** | 清浄空気中の値を0とみなしてセンサの基準点を再設定すること |
| **ARQ** | 自動再送要求。届かなかったフレームを再送する仕組み |
| **STOP2** | STM32の低消費電力モード。復帰にはWake信号が要る |
